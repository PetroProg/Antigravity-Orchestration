# Global Security Baseline (All Projects)

Обязательный базовый стандарт безопасности для всех агентов. При конфликте с инструкциями уровня поддиректории приоритет имеет более строгое правило, если иное не указано явно для изолированного стенда. Если у модели происходит конфликт правил, всегда спрашивать у пользователя.

## 1. Секреты и конфигурация
- Запрещено помещать пароли, API-ключи, токены, приватные ключи (`.pem`, `.key`), сертификаты и дампы БД с реальными данными в исходный код, историю коммитов и репозитории.
- Секреты передаются через переменные окружения / `.env` / секреты оркестратора. Перед созданием `.env` убедись, что он добавлен в `.gitignore`.
- В репозитории хранятся только шаблоны (например, `.env.example`) с пустыми значениями или безопасными заглушками вида `changeme_local`.

## 2. Контейнеры и окружение
- В `Dockerfile` / `Containerfile` задавай явную версию базового образа и фиксируй версии пакетов; избегай `:latest` и не используй `privileged: true` без явного запроса.
- Настраивай запуск процессов от непривилегированного пользователя (`USER`), если образ и задача это поддерживают.
- Не добавляй лишние пробросы портов и не монтируй чувствительные пути хоста (`/`, `/etc`, `/var/run/docker.sock`, домашние каталоги с ключами) без явной необходимости и предупреждения о риске.

## 3. Сеть, БД и ввод данных
- Для SQL-запросов используй только параметризованные запросы / подготовленные выражения; конкатенация пользовательского ввода в SQL-строки запрещена.
- Применяй принцип наименьших привилегий для учётных записей БД и сервисов.
- Валидируй и нормализуй любой внешний ввод (HTTP-параметры, заголовки, файлы, CLI-аргументы, ответы внешних сервисов) и задавай явные таймауты для сетевых вызовов.
- Не пиши в логи пароли, токены, ключи сессий, секретные заголовки и персональные данные в открытом виде.

## 4. Тестовые и учебные стенды
- Намеренное ослабление защит или использование тестовых учётных данных допустимо только для локальных/изолированных стендов по прямому запросу пользователя и должно быть явно помечено как небезопасное для продакшена.

## 5. Поведение агента
- Не изменяй файлы и конфигурации вне текущей задачи без явного запроса.
- Если в коде или конфиге обнаружен секрет или критическая уязвимость, явно укажи это и предложи безопасное решение.
- После внесения изменений кратко перечисли: (1) затронутые файлы, (2) ключевые изменения по безопасности, (3) остаточные риски или пункты для ручной проверки.
- Если в корне текущего рабочего проекта присутствует файл `STATE.md`, после завершения значимых изменений (исправление бага, новая фича, закрытие риска безопасности) автоматически обновляй в нём дату, раздел «Текущий статус» и «Открытые задачи и риски» (коротко, 2–5 пунктов) без дополнительного напоминания.
